## Context

Приложение прогноза уже отдаёт поэкранные выдачи для разделов «Модели»,
«Прогнозы», «Качество», «Сравнение»: один запрос к ручке раздела — всё для
отрисовки экрана. Факт продаж и расчёты моделей лежат в БД, но нигде не
собраны в выдачу, отвечающую на вопрос «выполним ли план».

Планы продаж в системе не хранятся вовсе — это изменение вводит их первым.
Мотивация — в `proposal.md` (Why).

## Goals / Non-Goals

**Goals:**
- Ввести хранение плана как документа с версиями
- Загрузить внешний план файлом, сопоставить со справочниками, сохранить версию
- Показать ожидаемый итог периода и разрыв по каждой строке разреза
- Ранжировать строки по вкладу в разрыв

**Non-Goals:**
- Расчёт плана системой — отдельное изменение
- Интерактивное сопоставление несопоставленных строк: результат показывается,
  правит его человек в файле
- Пересчёт по событию: контроль считается в момент открытия раздела
- Хранение слепка прогноза вместе с версией плана

## Decisions

### §1. Имя сущности: `plan_document`, а не `sales_plan`

План в предметной области — **документ, у которого есть период действия,
источник происхождения и версии**. `sales_plan` называет строку таблицы
и молчит про всё три: он звучит как «единственный действующий план»,
а планов на один период может сосуществовать несколько, и какой из них
действующий — решает специалист.

Имя `plan_document` едет дальше без переименований: в URL ручек
(`/sales-plan/documents/{id}`), в код сервиса и в подписи UI («документ
плана»). Спорить об имени после того, как оно разошлось по трём слоям,
поздно.

### §2. Версия неизменяема, правка создаёт новую

`plan_document_version` не обновляется после создания. Это следует прямо из
термина «версия плана» (снимок целиком на момент фиксации) и даёт бесплатно
то, ради чего обычно заводят аудит: ответ на вопрос «какая цифра стояла
десятого числа» — это чтение старой версии, а не восстановление истории
правок.

Альтернатива — одна таблица плана с обновлением на месте и журналом
изменений — отклонена: журнал изменений отвечает на вопрос «что поменяли»,
а специалисту нужен ответ на «что было», и восстанавливать состояние из
журнала пришлось бы кодом.

### §3. Версия ссылается на модель, но не на конкретный прогноз

`plan_document_version.model_id` указывает, какая прогнозная модель была
рабочей. Ссылки на конкретный расчёт прогноза **нет**: при каждом открытии
контроля ожидаемый итог считается заново, по актуальному факту и актуальным
расчётам модели.

Через версию плана проходит только план. Факт и расчёт модели через неё
**не проходят** — они читаются из своих таблиц в момент запроса.

Следствие, заметное пользователю: если между двумя открытиями раздела модель
переобучилась, ожидаемый итог изменится, хотя план тот же. Это не ошибка,
а свойство: контроль всегда говорит о сегодняшнем знании. Но пользователя,
ожидающего, что «цифры не поменяются», это удивит, и раздел подписывает
дату расчёта.

### §4. Ожидаемый итог считает сервер

Формула «факт + расчёт модели на остаток периода» живёт на сервере, клиент
получает готовую таблицу. Альтернатива — отдать факт и прогноз отдельно
и складывать в браузере — отклонена: логика раздваивается, тестировать
нечего, и любая правка формулы требует релиза фронта.

### §5. Сопоставление при загрузке — по коду, без интерактива

Файл содержит код магазина, код категории и величину. Наименования в файле
игнорируются: они служат только для человекочитаемости отчёта. Строки,
код которых не найден в справочнике, в версию не попадают и перечисляются
в ответе на загрузку.

Интерактивный маппинг «неизвестный код → известный» отложен осознанно:
он требует хранения правил сопоставления, то есть ещё одной сущности,
а первый же прогон покажет, насколько часто расхождения вообще случаются.

### §6. Схема данных

Единица величины хранится **на документе**, а не на значении: план целиком
измеряется в чём-то одном. Это и есть техническая форма
`БТ/sales-plan-control/1` — добавление денег будет новым значением enum,
а не миграцией структуры.

```sql
CREATE TYPE plan_unit AS ENUM ('qty', 'amount');
COMMENT ON TYPE plan_unit IS
  'Единица измерения плана. qty — штуки (единственная поддерживаемая сейчас); '
  'amount — деньги, значение заведено заранее, чтобы подключение выручки '
  'не требовало миграции (БТ/sales-plan-control/1).';

CREATE TYPE plan_version_source AS ENUM ('upload', 'calculated');
COMMENT ON TYPE plan_version_source IS
  'Происхождение версии. upload — загружена файлом извне; calculated — '
  'рассчитана системой. Значение НЕ названо по имени capability, которая '
  'её рассчитывает: capability переименуют, а данные в колонке останутся. '
  'На способ контроля происхождение не влияет: контролируются одинаково обе.';

CREATE TABLE plan_document (
    id            bigserial    PRIMARY KEY,
    title         text         NOT NULL,
    period_start  date         NOT NULL,
    period_end    date         NOT NULL,
    unit          plan_unit    NOT NULL DEFAULT 'qty',
    created_at    timestamptz  NOT NULL DEFAULT now(),
    created_by    bigint       NOT NULL REFERENCES app_user (id),
    CONSTRAINT plan_document_period_ck CHECK (period_end >= period_start)
);

COMMENT ON TABLE  plan_document IS
  'Документ плана продаж: период действия, единица измерения и владелец. '
  'Сами цифры лежат в версиях — документ их не хранит.';
COMMENT ON COLUMN plan_document.id IS
  'Суррогатный ключ документа.';
COMMENT ON COLUMN plan_document.title IS
  'Название, которое специалист видит в списке планов. Задаётся при загрузке.';
COMMENT ON COLUMN plan_document.period_start IS
  'Первый день планового периода включительно. Задаётся при загрузке, '
  'а не читается из файла: внешняя система дат не проставляет.';
COMMENT ON COLUMN plan_document.period_end IS
  'Последний день планового периода включительно.';
COMMENT ON COLUMN plan_document.unit IS
  'Единица измерения всех величин документа. Одна на документ: план целиком '
  'ставится либо в штуках, либо в деньгах.';
COMMENT ON COLUMN plan_document.created_at IS
  'Момент создания документа.';
COMMENT ON COLUMN plan_document.created_by IS
  'Специалист, загрузивший план.';

CREATE INDEX plan_document_period_idx ON plan_document (period_start, period_end);
COMMENT ON INDEX plan_document_period_idx IS
  'Основной доступ к списку планов — «какие планы действуют на эту дату». '
  'Строк в таблице сотни, индекс нужен не ради скорости, а ради плана '
  'запроса при джойне со списком версий.';

CREATE TABLE plan_document_version (
    id           bigserial            PRIMARY KEY,
    document_id  bigint               NOT NULL REFERENCES plan_document (id) ON DELETE CASCADE,
    version_no   integer              NOT NULL,
    source       plan_version_source  NOT NULL,
    model_id     bigint               NULL REFERENCES forecast_model (id),
    note         text                 NULL,
    created_at   timestamptz          NOT NULL DEFAULT now(),
    created_by   bigint               NOT NULL REFERENCES app_user (id),
    CONSTRAINT plan_document_version_uk UNIQUE (document_id, version_no)
);

COMMENT ON TABLE  plan_document_version IS
  'Неизменяемый снимок плана. После создания не обновляется: правка плана — '
  'это новая версия (design §2).';
COMMENT ON COLUMN plan_document_version.id IS
  'Суррогатный ключ версии.';
COMMENT ON COLUMN plan_document_version.document_id IS
  'Документ, которому принадлежит версия.';
COMMENT ON COLUMN plan_document_version.version_no IS
  'Порядковый номер версии внутри документа, с 1. Показывается специалисту.';
COMMENT ON COLUMN plan_document_version.source IS
  'Откуда версия взялась: загружена или рассчитана системой.';
COMMENT ON COLUMN plan_document_version.model_id IS
  'Рабочая прогнозная модель на момент создания версии. NULL для загруженного '
  'извне плана: он моделью не пользовался. Ссылки на конкретный расчёт '
  'прогноза здесь нет намеренно — контроль считается по актуальным данным '
  '(design §3).';
COMMENT ON COLUMN plan_document_version.note IS
  'Комментарий специалиста: почему появилась эта версия.';
COMMENT ON COLUMN plan_document_version.created_at IS
  'Момент фиксации версии. По нему отвечают на вопрос «что стояло десятого».';
COMMENT ON COLUMN plan_document_version.created_by IS
  'Специалист, зафиксировавший версию.';

CREATE TABLE plan_value (
    version_id   bigint         NOT NULL REFERENCES plan_document_version (id) ON DELETE CASCADE,
    store_id     bigint         NOT NULL REFERENCES store (id),
    category_id  bigint         NOT NULL REFERENCES category (id),
    plan_value   numeric(14,3)  NOT NULL,
    PRIMARY KEY (version_id, store_id, category_id)
);

COMMENT ON TABLE  plan_value IS
  'Плановая величина одной строки разреза «магазин × категория» внутри версии. '
  'Единица — та, что указана в plan_document.unit.';
COMMENT ON COLUMN plan_value.version_id IS
  'Версия, к которой относится значение.';
COMMENT ON COLUMN plan_value.store_id IS
  'Магазин из справочника системы. Строки файла, код которых не сопоставился, '
  'сюда не попадают (design §5).';
COMMENT ON COLUMN plan_value.category_id IS
  'Категория товара из справочника системы.';
COMMENT ON COLUMN plan_value.plan_value IS
  'Плановая величина. numeric, а не integer: деньги придут в этот же столбец, '
  'а три знака после запятой оставлены под весовые категории.';
```

**Объёмы и индексы.** Одна версия — строк по числу пар «магазин × категория»
в разрезе: сейчас 70, целевой масштаб — до 10 тыс. Версий на документ единицы,
документов в год порядка десятка на подразделение. Порядок `plan_value` за
год — сотни тысяч строк, за пять лет — единицы миллионов.

Отдельных индексов на `plan_value` **нет и не нужно**: единственный доступ —
«все строки версии» и «строки версии по подмножеству магазинов и категорий»,
и составной первичный ключ `(version_id, store_id, category_id)` закрывает
оба, потому что `version_id` идёт первым. Индекс по `store_id` был бы полезен
для запроса «все планы этого магазина за всё время» — такого сценария в
изменении нет, и заводить индекс под гипотезу означает платить за него
на каждой загрузке.

## Risks / Trade-offs

**[Загрузка принимает любой файл с тремя колонками]** → пользователь сразу
видит отчёт о сопоставлении и итоговую таблицу; неверный файл заметен по
числу несопоставленных строк или по неправдоподобным величинам. Схемной
валидации файла на первом этапе нет.

**[Ожидаемый итог меняется между открытиями раздела]** → раздел подписывает
дату и время расчёта, а также идентификатор рабочей модели. Свойство
объяснено в §3; убрать его можно только хранением слепка прогноза, что
противоречит смыслу контроля.

**[Пересечение планов не проверяется]** → две версии на один период и один
разрез могут сосуществовать. Для первого этапа допустимо: выбор плана для
контроля явный, специалист сам решает, какой действующий.

**[Разрез за пределами горизонта модели]** → если до конца периода дальше
7 дней, расчёт модели покрывает не весь остаток. В этом изменении остаток
за горизонтом оценивается нулём, и раздел говорит об этом прямо: «оценка
остатка покрывает 7 из 23 дней». Честная оценка длинного остатка — предмет
следующего изменения.

## Migration Plan

1. Миграция создаёт два enum и три таблицы. Данных для переноса нет —
   планов в системе до сих пор не было.
2. Откат — `DROP TABLE plan_value, plan_document_version, plan_document;`
   и `DROP TYPE plan_version_source, plan_unit;`. Безопасен: на эти таблицы
   ничто не ссылается.
3. Раздел меню появляется вместе с ручками; отдельного флага раскатки нет —
   пустой список планов и есть корректное первое состояние.
