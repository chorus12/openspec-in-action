## 1. Хранение плана

> **Терминология блока.** *Документ плана* (`plan_document`) — план как
> артефакт: период действия, единица измерения, владелец. *Версия*
> (`plan_document_version`) — неизменяемый снимок цифр на момент фиксации;
> правка плана создаёт новую версию, а не переписывает старую. *Значение*
> (`plan_value`) — одна строка разреза «магазин × категория» внутри версии.
> Почему `plan_document`, а не `sales_plan` — design §1; почему версия
> неизменяема — design §2.

- [x] 1.1 Миграция: два enum и три таблицы

  Хранение плана продаж, которого в системе до сих пор не было. DDL целиком —
  design §6, оттуда же комментарии к таблицам и ко всем колонкам: они едут
  в миграцию дословно и потом видны в pgAdmin. Индексов на `plan_value` не
  заводить — составной первичный ключ закрывает оба сценария доступа
  (design §6, абзац про объёмы).

- [x] 1.2 Модели SQLAlchemy и репозиторий версий

  Чтение и запись документа, версии и значений. Версия не обновляется после
  создания: метода `update` у репозитория нет вовсе, чтобы неизменяемость
  не держалась на договорённости.

- [x] 1.3 Тест: вторая загрузка создаёт версию, первая остаётся целой

  Закрывает сценарий «Повторная загрузка того же документа».

## 2. Загрузка плана файлом

- [x] 2.1 Разбор файла и сопоставление по коду

  Приём внешнего плана: файл → строки → коды магазинов и категорий →
  идентификаторы справочника. Наименования из файла в сопоставлении не
  участвуют и сохраняются только для отчёта о несопоставленных строках
  (design §5).

- [x] 2.2 Ручка `POST /sales-plan/upload`

  Загрузка одним запросом: файл и период плана на входе, документ с версией
  и перечень несопоставленных строк на выходе. Период приходит параметром,
  а не читается из файла — решение бизнеса, `business.md`, закрытый вопрос.

- [x] 2.3 Тесты загрузки: полное сопоставление и частичное

  Закрывают сценарии «Все строки файла сопоставлены» и «Часть строк не
  сопоставилась».

## 3. Расчёт контроля

- [x] 3.1 Сервис ожидаемого итога

  Ответ на вопрос «выполним ли план»: по каждой строке разреза — накопленный
  факт, оценка остатка периода по расчётам рабочей модели, ожидаемый итог
  и разрыв. Формула живёт на сервере целиком (design §4). Слепок прогноза не
  сохраняется: расчёт идёт по актуальным данным (design §3).

- [x] 3.2 Остаток за горизонтом модели

  Дни остатка, которые модель не покрывает, оцениваются нулём, а выдача несёт
  число покрытых и непокрытых дней. Раздел обязан сказать об этом вслух —
  иначе заниженный ожидаемый итог выглядит как заниженный прогноз.

- [x] 3.3 Разрез и агрегация по иерархии

  Произвольное подмножество магазинов × подмножество категорий; агрегация до
  региона и до группы категорий. Итоги считает сервер.

- [x] 3.4 Ранжирование по вкладу в разрыв и пороги существенности

  Список приоритетов: строки по абсолютному вкладу в разрыв, существенным
  считается отклонение, прошедшее одновременно относительный и абсолютный
  порог. Пороги — параметры запроса со значениями по умолчанию.

- [x] 3.5 Ручка `GET /sales-plan/control`

  Одна выдача на весь раздел: рабочая таблица, итоги разреза, список
  приоритетов, дата расчёта и идентификатор рабочей модели.

- [x] 3.6 Тесты расчёта

  Закрывают сценарии «Период пройден наполовину», «Период ещё не начался»,
  «Остаток периода длиннее горизонта модели», «Несколько магазинов и одна
  категория», «Агрегация магазинов до региона», «Крупная категория с малым
  процентом важнее мелкой с большим», «Мелкий шум не помечается
  существенным».
