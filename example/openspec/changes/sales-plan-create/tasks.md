## 1. Схема данных

> **Терминология блока.** *Бакет* — отрезок периода, на который разбит план:
> день, неделя, месяц или период целиком. *Автоплан* (`auto_value`) — цифра,
> предложенная системой; после расчёта неизменна. *Ручная корректировка*
> (`manual_adjustment`) — поправка специалиста со знаком, хранится отдельно.
> *Итоговый план* (`plan_value`) — их сумма; единственная колонка, которую
> читает контроль. Почему поправка отдельно, а не правится итог — design §4;
> DDL целиком — design §6.

- [x] 1.1 Миграция: два enum, пять колонок, расширенный первичный ключ

  Хранение плана с разбивкой по бакетам и раздельными величинами расчёта
  и правки. DDL и комментарии ко всем колонкам — design §6, оттуда же
  в миграцию дословно. Существующие строки получают `bucket_start` = начало
  периода и шаг `period`: это ровно то, чем они и были. Новых индексов
  не заводить — расширенный первичный ключ закрывает доступ (design §6,
  абзац про объёмы).

- [x] 1.2 Модели и репозиторий: запись версии пакетом

  Сохранение десятков тысяч строк одной транзакцией. Версия неизменяема,
  конкурентной записи в те же строки не бывает.

- [x] 1.3 Тест: миграция не портит загруженные извне версии

  У них три новые колонки NULL, а `plan_value` не трогается.

- [x] 1.4 `sales-plan-create` добавлена в `TRACKED`

  Делается вместе с появлением дельта-спеки, а не при архивации: не внесённая
  в `TRACKED` capability не видна ни в отчёте покрытия, ни в гейте, и до
  архивации об этом ничто не напомнит.

## 2. Оценка остатка и метод расчёта

- [x] 2.1 Модуль `remainder_estimate`

  Ответ на вопрос «сколько будет продано за интервал дат по этой паре
  магазин × категория». Общий для контроля и формирования — вторая копия
  разошлась бы на первой правке методики (design §1). Через модуль проходит
  только оценка будущего: ни документа, ни версии, ни корректировок он
  не знает.

- [x] 2.2 Выбор метода по интервалу и горизонту

  Таблица условий — design §2. Гибрид не смешивает источники на одном дне:
  граница — последний день горизонта.

- [x] 2.3 Исторический baseline

  Сезонно-трендовая оценка на дни за горизонтом. Коэффициент роста —
  открытый вопрос к бизнесу, блокирующий `БТ/sales-plan-create/2`;
  до ответа считаем «прошлый год как есть» и говорим об этом на экране.

- [x] 2.4 Тесты метода

  Закрывают сценарии «Период укладывается в горизонт модели», «Период
  длиннее горизонта», «Период начинается за горизонтом».

- [x] 2.5 Правка контроля: остаток считается новым модулем

  Закрывает сценарий «Остаток периода длиннее горизонта модели» в новой
  формулировке. Выкатывается вместе с модулем: раздельная выкатка дала бы
  период, в котором два раздела считают будущее по-разному (design, Migration Plan, шаг 2).

- [ ] 2.6 Источник данных оценки — протокол `EstimateSource`

  Модуль оценки получает расчёт модели и факт продаж через протокол,
  объявленный им самим, а не читает таблицы приложения прогноза (design §7).
  Протокол — в `remainder_estimate/source.py`, реализация `DbEstimateSource` —
  в `infra/forecast_db.py`, сборка — рядом с сервисами разделов. Тесты 2.4
  переводятся с базы на фейк по протоколу; `Mock(spec=DbEstimateSource)`
  не использовать.

- [ ] 2.7 Пара без истории: дни без оценки вместо нуля

  Отсутствующий день у источника — «данных нет», а не 0 (design §7, контракт
  на краях). Закрывает сценарии «У пары нет истории продаж» в обеих
  capability; фейк отдаёт словарь без прошлогодних дат.

## 3. Автоплан

- [ ] 3.1 Систематическое смещение модели

  Устойчивая склонность модели завышать или занижать по паре «магазин ×
  категория»: медиана относительной ошибки за последние N завершённых
  недель. Медиана, а не среднее — чтобы одна распродажа не сдвинула
  поправку на квартал вперёд (design §3). История ошибок приходит через
  `EstimateSource`: новая операция сначала дописывается в протокол, потом
  в `DbEstimateSource` и фейк (design §7).

- [ ] 3.2 Расчёт автоплана

  Расчёт модели минус смещение. Целевых надбавок нет и быть не должно —
  всё, что похоже на амбицию, вносит человек корректировкой
  (`БТ/sales-plan-create/3`).

- [ ] 3.3 Тесты автоплана

  Закрывают сценарии «Модель систематически занижает», «Смещения нет»,
  «Разовая распродажа не сдвигает поправку». Идут на фейке источника,
  без базы (design §7).

- [ ] 3.4 Ручка `POST /sales-plan/create`

  Одна выдача на раздел: рабочая таблица с расчётом модели и автопланом
  по бакетам, метод расчёта, число покрытых моделью дней, справочная
  колонка предыдущего плана.

## 4. Правка и фиксация

- [ ] 4.1 Раскладка бакетов по шагу детализации

  Закрывает сценарии «Месяц по неделям» и «Период одним куском». Неделя,
  частично попавшая в период, остаётся бакетом — усечённым по границам.

- [ ] 4.2 Ручная корректировка: хранение и арифметика итога

  Итог = автоплан + корректировка. Автоплан после расчёта не меняется.
  Закрывает сценарии «Правка одной строки» и «Возврат к автоплану».

- [ ] 4.3 Групповая правка на клиенте

  Раскладывается в значения корректировки выбранных строк; на сервер уходит
  полный набор при сохранении, отдельной серверной операции нет (design §4).
  Закрывает сценарий «Процентная правка группы».

- [ ] 4.4 Ручка `POST /sales-plan/create/save`

  Фиксация версии с периодом, шагом, моделью, методом и горизонтом.
  Закрывает сценарии «Фиксация сохраняет обстоятельства расчёта» и «Правки
  видны после фиксации версии».

- [ ] 4.5 Выгрузка `GET /sales-plan/export`

  Файл с раздельными колонками автоплана, корректировки и итога, по строке
  на бакет. Закрывает сценарии «Выгрузка различает расчёт и правку»
  и «Выгрузка сохраняет разбивку».
