# Инверсия зависимостей

Навык отвечает на один вопрос: **чей файл будут править, когда что-то изменится
снаружи**. Правила предметной области меняются редко и по решению бизнеса;
драйвер базы, SDK провайдера, фреймворк — часто и по чужим причинам. Инверсия
раскладывает изменения так, чтобы чужие чинились в инфраструктуре, а бизнес-правила
их не замечали (аксиома А3 — «зависимости направлены к стабильности»).

Полный разбор с примерами кода — `reference.md` рядом; ссылки ниже вида
«→ reference: <раздел>» ведут в его заголовки. Общая картина аксиом — навык
`architecture-axioms` (`openspec/architecture/axioms/SKILL.md`).

## Словарь

- **Домен** — код правил предметной области. **Инфраструктура** — код, говорящий
  с внешним миром (драйвер, HTTP-клиент, SDK, отправка писем).
- **Стрелка вызова** — кто кого дёргает во время работы; инверсия её не трогает.
  **Стрелка зависимости** — кто под кого подстраивается; инверсия разворачивает
  только её. → reference: «Две стрелки».
- **Внедрение (DI)** отвечает на вопрос «кто и где собирает объекты».
  **Инверсия (DIP)** — «кому принадлежит абстракция и в чьих она словах».
  Инверсии без внедрения не бывает; внедрение без инверсии — сплошь и рядом,
  особенно с DI-контейнером. → reference: «Итог: внедрение и инверсия».
- **Точка сборки** (`main.py`, `containers.py`) — единственное место, где домен
  встречается с инфраструктурой.

## Шаг 0. Нужна ли инверсия вообще

Сначала — нужна ли она здесь. Инвертировать стоит только **реальную ось изменений**:
внешний сервис, ввод-вывод, то, что вы не контролируете, вторая реализация, нужная
уже сейчас (в том числе фейк для теста бизнес-правила). Не инвертировать:
стандартную библиотеку, единственную внутреннюю реализацию, которую никто не
собирается заменять, воображаемые оси «на будущее» — это косвенность без выгоды
(А5, закон Галла). Выделить протокол из работающего кода дёшево; убрать ненужный,
когда на него завязались, дорого.

Ответ «не нужна» — полноценный результат навыка, его записывают с причиной.

## Порядок проверки

Для каждой пары «домен ↔ внешняя зависимость»:

1. **Кто кого чинит.** Если изменится этот модуль — чей файл придётся открыть?
   Прогони два изменения: «домену понадобилась новая операция» и «меняем поставщика»
   (PostgreSQL → MongoDB, Stripe → другой провайдер). Правильно: новая операция —
   строка в протоколе домена плюс метод в инфраструктуре; смена поставщика — новый
   класс в `infra/` плюс строка в точке сборки, файлы домена не открываются.
   → reference: «Проба на удаление и проба „кто кого чинит“».
2. **Проба на удаление.** Удали потребителя — абстракция потеряла смысл? Тогда она
   принадлежит ему. Осталась осмысленной (описание сессии базы, клиента API) —
   она принадлежит инфраструктуре, и инверсии нет. Владелец абстракции — тот,
   вместе с кем она теряет смысл.
3. **Три вопроса к протоколу.** → reference: «Три вопроса к протоколу».
   - *В чьих словах?* `get_by_id(user_id) -> dict`, `charge(customer, amount)` —
     слова домена. `fetch_one(sql, params) -> Row`, `table`, `Row`, `session` —
     слова поставщика; тогда перевод с языка базы вернулся в сервис.
   - *Где лежит?* В пакете потребителя (`users/service.py`, `billing/ports.py`),
     не в `infra/`.
   - *Кому принадлежит?* См. п. 2.
4. **Импорты файла сервиса.** Не ищи контейнер — открой файл сервиса и посмотри,
   куда смотрят импорты. Импорт из `infra/`, драйвера, ORM-модели или SDK — инверсии
   нет, как бы образцово ни выглядел контейнер.
5. **Точка сборки.** Все имена конкретных классов собраны в одном месте; время
   жизни (Singleton/Factory) решается там же, а не в классах.
6. **Контракт сверх сигнатуры (А4).** Что реализация делает, когда объекта нет:
   `None`, исключение, пустой словарь? Сигнатура молчит, тайпчекер пропустит все три.
   Место контракта — докстринг протокола и набор тестов, общий для всех реализаций.
7. **Протокол или абстрактный класс.** Тайпчекер в CI блокирует merge — `Protocol`
   (подходит и под чужие классы, фейк в три строки). Барьера нет — `ABC`
   с `@abstractmethod`: забытый метод уронит тест в любом окружении. Все реализации
   свои и им нужен общий код — `ABC`. На направление стрелки выбор не влияет.
   → reference: «Протокол или абстрактный класс».

## Признаки нарушения

Хватит одного, чтобы заподозрить: внедрение есть, инверсии нет. → reference: «Признаки нарушения».

- файл сервиса импортирует инфраструктуру (драйвер, ORM-модель, HTTP-клиент, SDK, `infra/*`);
- параметр конструктора объявлен конкретным классом: `repo: PostgresUserRepository`;
- абстракция названа в честь инструмента и лежит в `infra/` (`DbSession.fetch_one(sql, params)`);
- смена поставщика требует правок в `users/`, `billing/` и т. п.;
- тест бизнес-правила собирает объекты инфраструктуры: `mock.Mock(spec=PostgresUserRepository)`,
  ORM-объект `User(hashed_password=...)`, `stripe.PaymentIntent`.

## Режим design (артефакт `design.md`)

Если change вводит внешнюю зависимость и шаг 0 ответил «нужна», в **Decisions**
для каждой такой зависимости записать:

- **протокол** — имя в словах домена и его операции (сигнатуры), без слов поставщика;
- **где лежит** — модуль потребителя;
- **реализация** — класс в инфраструктуре и что он переводит (SQL, формат SDK → типы домена);
- **точка сборки** — где собирается и с каким временем жизни;
- **контракт на краях** — поведение при отсутствии объекта, ошибках поставщика;
- **чем подменяется в тестах** — фейк по протоколу.

Если шаг 0 ответил «не нужна» — одна фраза в **Risks / Trade-offs**: какую
зависимость сознательно не прячем и почему (так же, как записывается отказ
от индекса: следующий читатель не будет заводить абстракцию заново).

## Режим apply (пишется код)

- Новая операция, нужная сервису, **сначала** дописывается в протокол, потом —
  в реализацию и фейк. Тайпчекер тогда сам покажет всех отставших.
  → reference: «Одно изменение по шагам».
- Тест бизнес-правила идёт на **фейке по протоколу** (класс в несколько строк,
  без наследования от реализации и без импорта `infra/`), а не на
  `Mock(spec=<конкретный класс>)`. Mock — объект типа `Any`: он молча вернёт
  истинную пустышку на новый метод, и тест пройдёт по ветке, которую автор не
  выбирал. Фейк заставляет решить явно (активен ли пользователь и т. п.).
- Фейк отдаёт данные в словах домена, а не ORM-объекты: переименование колонки
  не должно ронять тесты сервиса.
- Если в проекте есть mypy/pyright — прогнать его по затронутым файлам: ошибка
  «FakeRepo is missing protocol member» — это найденное отставание, а не помеха.

## Режим ревью (по запросу)

Находки — в формате: **место** (файл/раздел design) → **признак** из списка выше →
**что сломается при каком изменении** (конкретно: смена поставщика, новый метод,
переименование колонки) → **предложение** (протокол в словах домена, где ему
лежать, что поменять в тесте). Отдельно перечислить зависимости, которые
инвертировать **не нужно**, с причиной. Если нарушений нет — так и сказать.
