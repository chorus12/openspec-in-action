# Гейт покрытия сценариев

Два файла, которые не остаются в `openspec/`, а переезжают в тестовую папку
проекта:

| Файл | Что это |
|---|---|
| `test_spec_coverage.py` | проверки и отчёт. Правится редко |
| `spec_coverage_data.py` | `TRACKED` и `MANUAL` — данные. Правятся почти в каждом change'е |

## Зачем это

Спека OpenSpec обещает: **каждый сценарий — потенциальный тест**. Обещание
ничем не подкреплено — сценарий можно написать, заархивировать и никогда не
проверить. Тогда `openspec/specs/` перестаёт быть описанием системы и
становится описанием намерений, а через полгода ему никто не верит.

Гейт считает не строки кода, а **сценарии**. Знаменатель — все
`#### Scenario:` из спек, числитель — те, на которые сослался тест или
расписка о ручной проверке.

Ключевое свойство: **до архивации гейт молчит**. Сценарии активного change'а
попадают только в отчёт — писать тесты на нереализованные блоки нечем, и
красный тест был бы шумом, который научатся игнорировать. Гейт включается сам
в тот момент, когда `openspec archive` переносит требование в
`openspec/specs/` — то есть когда оно становится постоянным.

## Установка

**1. Скопируй оба файла в тестовую папку проекта.**

```
tests/
├── test_spec_coverage.py
└── spec_coverage_data.py
```

Папка может быть любой (`tests/`, `backend/tests/`, `services/api/tests/`) —
корень репозитория ищется подъёмом вверх до первой папки, содержащей
`openspec/config.yaml`. Важно другое: файлы должны лежать **рядом друг с
другом**, и `test_spec_coverage.py` должен видеть остальные тесты — маркеры
он собирает регуляркой по `test_*.py` в своей директории.

**2. Зарегистрируй маркер `spec`.**

В `pyproject.toml`:

```toml
[tool.pytest.ini_options]
markers = [
    "spec(path): сценарий спеки, который закрывает этот тест — '<capability>/<Requirement>/<Scenario>'",
]
```

или в `pytest.ini`:

```ini
[pytest]
markers =
    spec(path): сценарий спеки, который закрывает этот тест
```

Без регистрации pytest выдаёт `PytestUnknownMarkWarning` на каждый маркер, а с
`--strict-markers` — падает. Сам гейт маркеры читает **регуляркой по
исходникам**, а не через API pytest: так покрытие считается без запуска
коллекции и не зависит от того, поднимается ли база. Но тесты с маркерами
запускаются обычным образом, и предупреждения посыпались бы на них.

**3. Заполни `TRACKED` в `spec_coverage_data.py`.**

```python
TRACKED = {"sales-plan-control", "sales-plan-create"}
```

Только перечисленные здесь capability попадают и в гейт, и в отчёт. Список
расширяется осознанно, по одной capability за раз: спеки, написанные до
введения механизма, вносить задним числом не надо — гейт станет красным
с первого дня, и первое, что с ним сделают, — отключат.

Новая capability добавляется сюда **в тот же момент**, когда появляется её
дельта-спека. Забыть — значит не увидеть её сценарии нигде.

**4. Прогони.**

```
python -m pytest tests/test_spec_coverage.py -s -q
```

`-s` обязателен: отчёт печатается через `capsys.disabled()`, без него его не
видно.

## Как закрыть сценарий тестом

Сценарий в спеке:

```markdown
### Requirement: Ожидаемый итог периода
Система SHALL показывать по каждой строке разреза ожидаемый итог периода.

#### Scenario: Период пройден наполовину
- **GIVEN** версия плана на период, половина которого прошла
- **WHEN** специалист открывает контроль плана
- **THEN** ожидаемый итог равен накопленному факту плюс оценка остатка периода
```

Тест, который его закрывает:

```python
@pytest.mark.spec("sales-plan-control/Ожидаемый итог периода/Период пройден наполовину")
def test_expected_total_is_fact_plus_remainder():
    ...
```

Строка в маркере — **дословный путь** `<capability>/<Requirement>/<Scenario>`:
имя папки capability, затем текст после `### Requirement: `, затем текст после
`#### Scenario: `. Ни сокращений, ни перефразирования: гейт сверяет строки, а
не смыслы. Переименовали сценарий — `test_markers_point_at_existing_scenarios`
покраснеет и назовёт, какой именно маркер осиротел.

Один тест может нести несколько маркеров, если закрывает несколько сценариев.

## Как закрыть сценарий распиской

Часть требований автотестом не берётся: вёрстка в браузере, поведение языковой
модели, свойство всей цепочки доставки (небуферизованность потока не видна
тесту, который читает ответ целиком). Для них — `MANUAL`:

```python
MANUAL = {
    # Ранжирование строк по вкладу в разрыв проверяется глазами: автотест
    # на подставных данных проверил бы подставную сортировку.
    "sales-plan-control/Список приоритетов/Крупная категория с малым процентом":
        "docs/sales-plan-control-check.md",
}
```

Значение — путь к **протоколу ручной проверки** относительно корня
репозитория. Протокол — не отписка: чекбоксы, под каждым — какой сценарий он
закрывает, внизу раздел «Результат прогона» с датой и окружением.

`MANUAL` ничего не проверяет. Гейт лишь следит, что сценарий существует
(`test_manual_entries_are_valid`), что протокол лежит на месте (там же) и что
на сценарий не навешаны одновременно тест и расписка
(`test_no_scenario_is_covered_twice_by_manual_and_test` — иначе забытая
расписка переживёт появление настоящего теста и будет врать).

Заполнять `MANUAL` **сознательно неудобно**: добавить расписку должно быть
дороже, чем написать тест. Ценность записи — в комментарии над ней, который
объясняет, почему автотест здесь невозможен, а не в самой строке.

Перечитывать `MANUAL` надо при архивации change'а: расписка действительна
ровно настолько, насколько актуален протокол, на который она ссылается.

## Что именно проверяется

| Проверка | Когда краснеет |
|---|---|
| `test_markers_point_at_existing_scenarios` | маркер ссылается на сценарий, которого в спеках нет: переименовали или удалили требование |
| `test_manual_entries_are_valid` | запись в `MANUAL` указывает на несуществующий сценарий или на пропавший протокол |
| `test_no_scenario_is_covered_twice_by_manual_and_test` | на сценарий есть и тест, и расписка — расписка забыта, её надо убрать |
| `test_archived_scenarios_are_covered` | **гейт**: сценарий из `openspec/specs/` (capability в `TRACKED`) не покрыт ничем |
| `test_report_change_coverage` | никогда: это отчёт, не проверка |

## Пример отчёта

Прогон на `example/` из этого репозитория. Заархивирована одна capability
(`sales-plan-control`), активен один change (`sales-plan-create`), доведён
до тестов один его блок:

```
$ python -m pytest tests/test_spec_coverage.py -s -q
....
sales-plan-create — покрытие сценариев: 7/21
  sales-plan-control  4/5
         -  Версия, сформированная системой, контролируется так же   (Ожидаемый итог периода и разрыв с планом)
         +  Остаток периода длиннее горизонта модели   (Ожидаемый итог периода и разрыв с планом)
         +  Период ещё не начался   (Ожидаемый итог периода и разрыв с планом)
         +  Период пройден наполовину   (Ожидаемый итог периода и разрыв с планом)
         +  Рабочая модель не выбрана   (Ожидаемый итог периода и разрыв с планом)
  sales-plan-create  3/16
         -  Модель систематически занижает   (Автоплан нейтрален)
         -  Разовая распродажа не сдвигает поправку   (Автоплан нейтрален)
         -  Смещения нет   (Автоплан нейтрален)
         +  Период длиннее горизонта   (Метод расчёта выбирается по данным и называется на экране)
         +  Период начинается за горизонтом   (Метод расчёта выбирается по данным и называется на экране)
         +  Период укладывается в горизонт модели   (Метод расчёта выбирается по данным и называется на экране)
         -  Выгрузка сохраняет разбивку   (Период планирования и шаг детализации)
         -  Месяц по неделям   (Период планирования и шаг детализации)
         -  Период одним куском   (Период планирования и шаг детализации)
         -  Возврат к автоплану   (Расчёт, автоплан, корректировка и итог видны и хранятся раздельно)
         -  Правка одной строки   (Расчёт, автоплан, корректировка и итог видны и хранятся раздельно)
         -  Правки видны после фиксации версии   (Расчёт, автоплан, корректировка и итог видны и хранятся раздельно)
         -  Процентная правка группы   (Расчёт, автоплан, корректировка и итог видны и хранятся раздельно)
         -  Выгрузка различает расчёт и правку   (Фиксация версии и выгрузка)
         -  Незафиксированные правки не переживают перезагрузку   (Фиксация версии и выгрузка)
         -  Фиксация сохраняет обстоятельства расчёта   (Фиксация версии и выгрузка)
.
5 passed in 0.01s
```

Как это читать:

- `7/21` — по активному change'у закрыт каждый третий сценарий. Это **не
  повод для красного**: блоки 3–5 его `tasks.md` ещё не сделаны, писать тесты
  не на что;
- `+` — закрыт тестом, `MANUAL` — закрыт распиской, `-` — не закрыт ничем;
- **заархивированных capability в отчёте нет.** Их держит гейт
  `test_archived_scenarios_are_covered`: пока он зелёный, все 14 сценариев
  `sales-plan-control` в `openspec/specs/` закрыты — 12 тестами и 2 расписками;
- строка `sales-plan-control  4/5` внутри отчёта по change'у — это его
  **дельта** к уже заархивированной capability: change меняет одно требование
  и добавляет ему сценарий, который ещё не закрыт;
- `5 passed` — это пять проверок самого гейта, а не пять тестов бизнес-логики.

Момент, ради которого стоит смотреть на этот отчёт: строка `-  Версия,
сформированная системой, контролируется так же`. Пока change активен, она
безобидна. В день архивации она станет требованием в `openspec/specs/`, и
`test_archived_scenarios_are_covered` покраснеет — то есть archive нельзя
делать, пока сценарий не закрыт тестом или распиской.

## Почему данные отделены от кода

`MANUAL` разрастается до сотен строк — по строке на каждый сценарий, который
проверяется руками, плюс комментарии, объясняющие почему. В одном файле
с проверками это означает, что каждый диффом идущий на ревью change показывает
данные вперемешку с логикой, а логика при этом не менялась.

Формат — Python-модуль, а не JSON или YAML: комментарий над записью `MANUAL`
несёт не меньше смысла, чем сама запись, и в JSON его написать негде.

Модуль называется `spec_coverage_data.py`, а не `test_spec_coverage_data.py`,
именно потому, что `marked()` ищет маркеры регуляркой по `test_*.py`: строки
`MANUAL` попали бы в выборку и засчитались как покрытие тестом.
